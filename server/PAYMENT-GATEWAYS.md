# Payment gateway setup and verification

Commerce-15 supports COD, MoMo/VNPAY sandbox adapters and payOS integration.
All online gateways default to disabled. Mock endpoints are test fixtures and
are not packaged in the application. Existing MOCK records remain readable.

## Local configuration

1. Use the existing Commerce-14 schema. For an existing database, stop the app,
   review and apply `src/main/resources/db/manual/commerce15-payment.sql` with
   your normal database client. It adds columns/keys and extends enum checks;
   it does not delete rows. Keep a database backup before applying to retained data.
   The script is not auto-run at startup. Fresh Testcontainers schemas are generated by JPA.
2. Set the variables in `payment.env.example` in the server process environment.
   Spring does not load that example file automatically. Do not commit credentials.
3. Register merchant sandbox credentials with MoMo/VNPAY. Enable one provider at a time.
   Enabled providers require credentials and valid HTTPS API/callback URLs at startup.
4. Expose the API via public HTTPS. Include the application's context path, if any,
   when setting callback URLs. MoMo receives its IPN URL in the create request.
   Register the VNPAY IPN URL with the merchant configuration; the configured
   `VNPAY_CALLBACK_URL` documents/validates that address, it is not sent as a pay parameter.
5. `PAYMENT_RETURN_BASE_URL` is the frontend origin (localhost allowed for sandbox).
   Return goes to `/profile/orders/{orderCode}?paymentReturn=1`. Query parameters
   do not update financial status. The logged-in owner page reads backend state.
6. Checkout lists enabled providers. Disabled/unconfigured providers never fall
   back to mock. COD remains available. Backend requests use ONLINE + provider.

payOS has **no sandbox**. Its adapter tests use local fixtures without credentials;
`PAYOS_ENABLED=false` must remain until a human separately authorizes a real-money
smoke test and configures a linked bank account. Webhook confirmation is a separate
operator action in payOS, not a startup API call. Its signed sample is acknowledged
without creating a fake order. No live gateway call has been verified by implementation tests.

## Runtime contract

- Server derives amount/currency from Order. Supported integration range: MoMo
  1,000–50,000,000 VND; VNPAY 5,000–999,999,999 VND; payOS 1–999,999,999 VND,
  whole VND only. These application limits can be narrower than merchant limits.
- POST `/orders/{orderCode}/payments/checkout` with `Idempotency-Key: <UUID>` and
  `{"provider":"MOMO"}` (or VNPAY/PAYOS). Owner only. Same key replays the same
  attempt even after failure. Different keys can reuse an active attempt; receipts
  persist that mapping. A new attempt requires a confirmed non-payment outcome.
- Attempt IDs are persisted before outbound HTTP. Merchant correlation and gateway
  transaction reference are separate. A timeout stays UNKNOWN, blocks another
  charge, and schedules query. The worker never blindly repeats a remote create
  after losing its response. If no recoverable checkout URL remains, status/query
  and eventual review are available; a new charge is not offered while uncertain.
- Each online Order has a fixed deadline from the initial Payment, default 15 minutes.
  Retries inherit it. Creation decrements stock once. Expiry/cancellation uses existing
  inventory/voucher compensation once; confirmed payment does not decrement again.
- Callbacks/query apply under Order row lock, with refreshed JPA entities across
  HTTP transaction boundaries. Payment, Order confirmation and history commit together.
  PostgreSQL uniquely limits applied_order_id and provider transaction reference.
- Success received after deadline/cancellation is retained and flagged LATE_SUCCESS.
  A second charge is EXTRA_PAYMENT/review. No automatic reopen or refund. Provider
  failure cannot downgrade success. Financial success and order fulfillment are separate.
- Local cancellation does not cancel money movement at the gateway. Queries continue
  for unresolved initiated attempts. Batch workers use persisted leases (90 seconds),
  bounded backoff (up to 15 minutes), max 96 queries and a 24-hour window by default.
  Exhaustion or inconsistent data requires review, never a fabricated final status.
- VNPAY ACK: 00 recorded, 02 duplicate/conflict, 01 unknown, 04 mismatch, 97 signature,
  99 processing error. MoMo commits then returns 204; payOS commits then returns 2xx.
- Only whitelisted correlation/money/outcome evidence is stored in raw_payload.
  Secrets, signatures, bank/account details and customer callback payload are omitted.
  Customer/admin API responses omit raw_payload. Evidence follows the Payment record's
  retention; no automated deletion job is introduced here.

## Operator review

Open Admin → Orders → order detail → Các lần thanh toán. Review reason identifies
late success, extra payment, amount/identity inconsistency or exhausted reconciliation.
Use the displayed transaction reference and merchant attempt ID (Payment ID for newly
created online attempts) to inspect the merchant portal. A financial status PAID does
not reopen a CANCELLED order. Contact the customer and handle any refund through the
provider's operator process; this module has no refund or manual-mark-paid endpoint.
For an additional transaction on the same attempt, the original reference stays on
the Payment; sanitized evidence/review reason preserves the unexpected reference.
Application logs identify failed worker payment IDs without printing credentials/payload.

## Manual UAT (UAT PENDING)

1. All flags false: COD create/delivery/cancel and disabled online API rejection.
2. VNPAY sandbox enabled: successful/declined payment, close browser, return/reload;
   assert backend state and one confirmation/history, no second stock movement.
3. MoMo test enabled: repeat those cases. Send a duplicate signed IPN; alter amount
   or signature and assert no confirmation. Return URL edits alone cannot mark paid.
4. Interrupt callback delivery; query job must recover confirmed success. Simulate
   remote timeout and restart; no new merchant charge is created while UNKNOWN.
5. Cancel/expire an unpaid order then deliver a sandbox success: CANCELLED order,
   retained financial success, exactly one stock/voucher reversal, admin review.
6. Retry a confirmed failed attempt with the old key then a new key: old replays;
   new creates one attempt, keeping original deadline. Two browser tabs cannot
   create concurrent unresolved attempts or access another user's order payments.
7. Separately authorized payOS live UAT: small real payment, registered webhook,
   return/reload and reference reconciliation. Do not infer this PASS from offline tests.
